# ADR-001: Вибір архітектурного стилю

## Статус
Прийнято

## Контекст
Expense Tracker — це REST API для обліку особистих витрат на Node.js + Express.
Проєкт розробляється однією особою в рамках навчального курсу.
Система включає автентифікацію, CRUD-операції, аналітику та звіти.
Потрібна архітектура, яка є простою у розумінні, легкою у підтримці
та відповідає розміру команди і складності задачі.

## Рішення
Використовувати Layered Architecture (шарова архітектура) з патерном MVC,
реалізований через Express.js.

Шари системи:
- **Presentation Layer**: routes/ + controllers/ — обробка HTTP-запитів
- **Business Logic Layer**: services/ — бізнес-правила та логіка
- **Data Access Layer**: repositories/ + models/ — робота з базою даних

## Альтернативи, що розглядалися

- **Мікросервіси**: відхилено, бо проєкт розробляється однією особою,
  а мікросервіси вирішують проблеми великих команд (50+ осіб).
  Для навчального проєкту це надмірна складність.

- **Моноліт без шарів (Spaghetti)**: відхилено, бо змішування бізнес-логіки,
  роботи з БД і HTTP-обробників робить код важко підтримуваним.
  Зміна бази даних вимагала б переписування всього коду.

- **Clean Architecture**: відхилено, бо надмірно складна для CRUD-застосунку.
  Доцільна при дуже складній бізнес-логіці та великій команді.

## Наслідки

+ Чіткий розподіл відповідальності між шарами
+ Легко замінити базу даних — зміни лише в repositories/
+ Легко тестувати кожен шар окремо
+ Зрозуміла структура для будь-якого розробника знайомого з MVC
- Більше файлів і папок порівняно з простим монолітом
- Потрібна дисципліна: не допускати витоку логіки між шарами
